# Benchmark Methodology: C++ vs Python on MNIST

How to benchmark the new standalone optimized C++ WiSARD against the
existing `wisardpkg` (already C++ under pybind11) and an optional pure-Python
reference, fairly, on MNIST. This answers the maintainer's open question
("I'm not sure how benchmarking C++ vs Python works"): the comparison is only
meaningful if every contender consumes the **same binarized+mapped input** and
reaches the **same accuracy** — then the wall-clock delta isolates the
train/classify kernel, not binarization or a luckier random mapping.

Deliverable notebook: `notebooks/benchmark/mnist_benchmark_publicavel.ipynb`
(headless via `nbconvert --execute`, results cached to `/tmp/*.json`).

See also: [build-and-testing.md](build-and-testing.md) (standalone header,
`make geninclude`), [mapping.md](mapping.md) (`RandomMapping`),
[binarization.md](binarization.md) (`SimpleThermometer`),
[classification-models.md](classification-models.md) (`Wisard.train/classify`),
[rams-and-discriminators.md](rams-and-discriminators.md) (address computation).

## The three contenders

| # | Contender | What it measures | How it is timed |
|---|-----------|------------------|-----------------|
| 1 | **standalone C++** | the new optimized kernel, no Python in the loop | external binary; wall-time via `subprocess` + a results JSON the binary emits |
| 2 | **wisardpkg** (pybind11) | the shipped C++ kernel as called from Python | in-process, `time.perf_counter()` around `w.train(ds)` / `w.classify(ds)` |
| 3 | **pure-Python WiSARD** (optional) | the "how slow is interpreted Python" floor | in-process, `time.perf_counter()` |

Contender 1 is built from the standalone header (`include/wisardpkg.hpp`,
generated by `make geninclude`; see [build-and-testing.md](build-and-testing.md)).
`test.cc` at the repo root is the reference for the standalone C++ API:
`wp::Wisard w(addressSize); wp::DataSet ds(X, y); w.train(ds); w.classify(ds);`.
The benchmark binary differs from `test.cc` only in that it (a) loads the shared
artifact instead of hardcoded rows and (b) prints timings as JSON to stdout.

Contender 3 is a ~40-line NumPy/dict WiSARD (RAM = `dict[tuple_bits → count]`,
one dict per RAM per class). It is **optional** and exists to bound the speedup:
if C++ is 200× faster than pybind11 but pybind11 is 5000× faster than pure
Python, that framing is the point. Skip it (`RUN_PYTHON_REF = False`) when only
the C++-vs-C++ delta matters.

## Fairness protocol (the crux)

The notebook prepares MNIST **once** and dumps a single shared artifact that
every contender reads. Nothing downstream re-binarizes or re-maps.

```
load MNIST (60k train / 10k test, fixed split)
  → binarize with ONE chosen thermometer  (SimpleThermometer, thermoSize bits/pixel)
  → build ONE RandomMapping               (fixed seed)
  → dump binarized rows + the mapping + labels to a shared artifact
        /tmp/mnist_prepared.npz   (binary rows, labels)
        /tmp/mnist_mapping.json   (the RAM→bit-index lists, per addressSize)
```

Why each piece is pinned:

| Pinned thing | If not pinned | Consequence |
|---|---|---|
| binarization (thermometer kind + `thermoSize`) | each contender binarizes its own way | accuracy diverges; you are comparing encoders, not kernels |
| random mapping (RAM→bit assignment) | each contender draws its own mapping | accuracy varies by mapping luck; speed numbers become noise |
| seed | non-deterministic mapping/shuffle | runs not reproducible; CI cannot regression-test |
| 60k/10k split | different train/test rows | accuracy not comparable |

The C++ `Wisard` consumes the **same** mapping because its JSON config accepts
an injected mapping: `c["mapping"]` is fed straight into
`mappingGenerator->setMappings(...)` (`src/models/wisard/wisard.cc:46`),
bypassing `RandomMapping::createMapping`. So the notebook builds the mapping
**once** (e.g. in Python via `wp.RandomMapping(entrySize, addressSize)` seeded,
or directly as index lists), writes it to `/tmp/mnist_mapping.json`, and:

- **wisardpkg** loads it via `wp.Wisard(json_config_with_mapping)`.
- **standalone C++** loads the same JSON and constructs `wp::Wisard(config)`
  (`src/models/wisard/wisard.cc:3`, the `nl::json` ctor).
- **pure-Python** reads the same index lists directly.

`DataSet(vector<vector<short>>, vector<string>)`
(`src/data/dataset.cc:64`) ingests the raw binary rows with no re-encoding —
both C++ paths feed it the artifact rows verbatim.

**Accuracy gate.** Before reporting any speed number, assert all contenders
reach the same accuracy within noise (e.g. `abs(acc_i − acc_ref) < 0.005`). If
they don't, the inputs diverged somewhere — a speed comparison on diverged
inputs is invalid. Print the accuracy table first; only then the timing table.

## Metrics

| Metric | Definition | C++ source | Python source |
|---|---|---|---|
| **train wall-time** | seconds to `train()` over 60k | `clock()` / `chrono::steady_clock` around `w.train(ds)`, emitted in JSON | `time.perf_counter()` around `w.train(ds)` |
| **inference latency** | per-sample classify time, **p50 / p99** | per-sample `chrono` deltas dumped as an array | per-sample `perf_counter` deltas → `np.percentile` |
| **throughput** | samples/s = 10000 / total_infer_time | derived | derived |
| **peak RSS** | max resident set | `getrusage(RUSAGE_SELF).ru_maxrss`; on macOS wrap with `/usr/bin/time -l` and parse "maximum resident set size" | `resource.getrusage(RUSAGE_SELF).ru_maxrss` or `tracemalloc.get_traced_memory()[1]` |
| **on-disk model size** | bytes of the serialized model | `w.json()` written to file, `stat().st_size` (`src/models/wisard/wisard.cc:180`) | same `w.json()` path via pybind11 |
| **accuracy** | top-1 on 10k test | argmax of class votes vs label | same |

`ru_maxrss` is **bytes** on macOS/Darwin but **kilobytes** on Linux — normalize
per platform (`sys.platform`). For the standalone binary, prefer the
`/usr/bin/time -l` wrapper on macOS (`-v` on GNU/Linux) because it captures the
whole process including allocator high-water marks the in-process `getrusage`
might miss across the train→classify boundary.

**Sweep.** Vary `addressSize ∈ {4, 8, 16, 28}` (and optionally
`thermoSize ∈ {2, 4, 8}`) to show how the C++/Python gap scales: bigger
`addressSize` → more RAMs / larger address space → the per-sample inner loop
(`RAM::getIndex`, `src/models/wisard/ram.cc:208`) dominates, which is exactly
where the interpreter tax compounds. Plot speedup vs `addressSize`.

## Hygiene

| Rule | Why |
|---|---|
| **warmup run** discarded before timing | first call pays page-fault / JIT / cache-cold costs |
| **≥5 reps**, report mean ± std and 95% CI | single runs are noise; CI = `1.96·std/√n` |
| **fixed seeds** everywhere (mapping, any shuffle) | reproducible, CI-regressable |
| **identical 60k/10k split** across contenders | accuracy comparability |
| **single-thread vs multi-thread reported separately** | never average across thread counts; they are different machines |
| **pin `OMP_NUM_THREADS`** (and `OPENBLAS_NUM_THREADS`) | the standalone binary and any BLAS in the Python floor must not silently grab all cores mid-sweep |
| **note macOS turbo / E-core variance** | Apple Silicon migrates threads between P- and E-cores and throttles under thermal load; averaging ≥5 reps + reporting std surfaces this rather than hiding it. Pin to a quiet machine; if available, document whether runs landed on P-cores |

Single-thread is the honest kernel comparison. wisardpkg's `Wisard` is
single-threaded today, so contender 2 is single-thread by construction; run the
standalone binary with `OMP_NUM_THREADS=1` for the apples-to-apples row, then a
separate multi-thread row if the new C++ parallelizes train/classify.

## MNIST acquisition

No MNIST is present locally (only CIFAR / cardio / etc.). Two cached options:

**Preferred — sklearn (no torch needed):**

```python
from sklearn.datasets import fetch_openml
import numpy as np, os
CACHE = '/tmp/mnist_openml'
X, y = fetch_openml('mnist_784', version=1, as_frame=False,
                    return_X_y=True, data_home=CACHE)
X = X.astype(np.float32)           # 70000 × 784, pixel 0..255
y = y.astype(int)                  # labels '0'..'9' → int
Xtr, ytr = X[:60000], y[:60000]    # canonical split
Xte, yte = X[60000:], y[60000:]    # last 10k = test
```

`fetch_openml` returns the rows already in canonical MNIST order, so
`[:60000]/[60000:]` is the standard split. `data_home` caches the download
under `/tmp` so re-execution is offline.

**Alternative — torchvision (torch is already the `[torch]` extra):**

```python
from torchvision.datasets import MNIST
import numpy as np
tr = MNIST('/tmp/mnist_torch', train=True,  download=True)
te = MNIST('/tmp/mnist_torch', train=False, download=True)
Xtr = tr.data.numpy().reshape(60000, 784).astype(np.float32); ytr = tr.targets.numpy()
Xte = te.data.numpy().reshape(10000, 784).astype(np.float32); yte = te.targets.numpy()
```

Either way the next step is identical: binarize once
(`SimpleThermometer(thermoSize, 0, 255)`), build one seeded mapping, dump the
shared artifact. The thermometer encodes each pixel into `thermoSize` bits, so a
784-pixel image becomes a `784·thermoSize`-bit `BinInput`
(`src/binarization/thermometer.cc:7`).
